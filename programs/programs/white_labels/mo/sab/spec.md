# Supplemental Aid to the Blind (MO) — Program Spec

- **Program key**: `mo_sab` (proposed — no calculator exists yet)
- **Base federal program**: none — a state cash supplement paid alongside SSI
- **White label**: MO
- **Engine**: PolicyEngine (recommended) — `mo_ssp` (`policyengine_us/variables/gov/states/mo/dss/ssp/`)
- **Added to MFB**: not added — Discovery
- **Spec last updated**: 2026-10-01
- **Sources captured**: 2026-09-11 (16 snapshots), 2026-09-18 (12 snapshots), 2026-09-21 (24 snapshots) and 2026-10-01 (7 snapshots) — 59 in total, of which 53 are cited; the 2026-09-11 set was re-verified against its manifest hashes on 2026-09-18, and all quoted fragments were re-found live on 2026-09-21. The 2026-09-21 set closes the SAB manual's own subtree: 54 sections exist and 19 are now captured, against 13 before that date. Two subtrees are complete: the December 1973 §1055.000.00 Vision (AB) chapter, whose index serves a password prompt but whose three leaves do not (§1055.020.00 and beyond return 404), and MO HealthNet for Families §1805.020.10, which §0405.030.00 routes citizenship to. The December 1973 §1015, §1020 and §1030 chapters are password-walled in full

**Scope.** This spec covers Supplemental Aid to the Blind. The recommended PolicyEngine calculator, `mo_ssp` ("Missouri State Supplementary Payment"), also models Supplemental Nursing Care, and Missouri runs a third blind cash program, Blind Pension. Both are out of scope — see Related Programs. The MFB program key is `mo_sab` rather than `mo_ssp` so that it names what this spec covers, not the whole calculator.

## Covered Eligibility Criteria

Criteria 1–10, 12 and 13 must all hold: every one must hold. **Criterion 11 is the exception** —
it is recorded here because Missouri states it in its eligibility chapter, but it is an election
between two programs rather than a gate, nothing is read for it, and nothing may suppress the
program on it. See the criterion; the build-side instruction is in the companion's Build requirements.

1. **Applicant must be age 18 or older**
   - Evaluation scope: `member`
   - Captured via: `birth_year_month` (`HouseholdMember`, DateField) via accessor `calc_age()`
   - Implementation note: on the recommended engine the gate is PolicyEngine's `mo_ssp_age_eligible`, which compares `age` against `ssp/age_threshold/sab` — 18, matching this criterion. `age` is a PolicyEngine *input*, so it reaches the engine only through `dependency.member.AgeDependency`, which `mo_sab` must declare as a `pe_input`. **Unsent it does not fail closed**: PolicyEngine's `age` carries `default_value = 40`, which *clears* the age-18 threshold rather than failing it, so an omitted `AgeDependency` would return **eligible** for scenario 5's 17-year-old. Scenario 5 is therefore the case that detects the omission. See the `pe_inputs` bullet in Known scenario gaps.

2. **Applicant must meet the state definition of blindness**
   - Evaluation scope: `member`
   - Captured via: `visually_impaired` (`HouseholdMember`, BooleanField, nullable)
   - Implementation note: `visually_impaired` is an inclusive self-report proxy for a formal determination, never a reproduction of the acuity standard. **Missouri's standard is 5/200, or a best visual field of 5 degrees**, and it is far stricter than the 20/200 that "legally blind" ordinarily means in the United States. §0405.025.00 routes the requirement to the December 1973 §1055.000.00 Vision (AB) chapter; that chapter's *index* serves a password prompt, but its three leaves do not, and §1055.005.00 Blindness (AB Eligibility Criteria) states the standard outright. RSMo §209.040.1 sets the same standard for Blind Pension in different words, corroborating §0425.015.00's statement that "the vision and age requirements for BP and SAB are the same". §1050.005.00's "more than 20/200" is a **different** number for a **different** person — it defines a **sighted spouse** for Data Gap 2's support rule, not the claimant. **Assert no threshold and never add a numeric acuity cutoff**: the screener holds a self-reported boolean and cannot evaluate 5/200. See Data Gap 1, whose over-inclusion is correspondingly wide. On the recommended engine the fact reaches PolicyEngine only through `dependency.member.IsBlindDependency` (`field = "is_blind"`, returning `member.visually_impaired or False`), which `mo_sab` must declare as a `pe_input`: `mo_ssp_category_eligible` gates this program on `(mo_ssp_living_arrangement == SAB) & is_blind`, and `is_blind` is a plain input defaulting to False, so unsent it returns $0 for every Missourian. **Scenario 4 does not cover this** — with `is_blind` withheld it still denies. See the `pe_inputs` bullet in Known scenario gaps.

4. **Applicant must be a U.S. citizen or qualified non-citizen**
   - Evaluation scope: `config`
   - Captured via: config `legal_status_required`
   - Implementation note: **the controlling rule set is MO HealthNet for Families', not Appendix K's summary phrase, and it is now captured and settled.** §0405.030.00 routes SAB's citizenship and immigrant status requirement to §1805.020.00 of the MAGI manual — "the same as for MO HealthNet for Families (MHF)". §1805.020.10 defines the qualified immigrant; §1805.020.10.10.10 imposes a five-year period of ineligibility on those entering on or after 1996-08-22, naming **Lawful Permanent Resident** first, and waives it for active-duty members, veterans, their spouses and dependent children, and unmarried surviving spouses; §1805.020.10.10.05 lists the statuses with **no** waiting period, which include refugees, asylees, Cuban and Haitian entrants, and those whose deportation has been withheld — and do **not** include permanent residents. So the long-standing question resolves: **`gc_5less` does not belong in the list** (an LPR of under five years is barred, except under the military waiver, which the screener cannot observe), and `citizen`, `refugee` and `gc_5plus` are each confirmed against the controlling section. The remaining entry is `otherWithWorkPermission`, which has **no counterpart** in §1805.020.10's enumeration — work authorisation is not itself a qualified status. **`config-review` examined it on 2026-10-01 and it stays**, on three grounds. MFB has already reasoned about this exact label, in benefits-api's shipped guard test `programs/management/commands/tests/test_five_year_bar_legal_statuses.py`. The comment is written over that test's eight Lifeline entries, but its reasoning is about what the bucket *contains* rather than about Lifeline: "`otherWithWorkPermission` stays: the bucket mixes qualified aliens subject only to the five-year clock with lawfully present statuses that never clear the qualified-alien gate at all, so removing it would over-exclude. A scoped warning banner carries that distinction instead." **That compensating control is not shipped, and Implement should know the over-inclusion stands uncompensated.** Read at `benefits-api` `origin/main` `f2a2e6d9`, 123 configs declare `otherWithWorkPermission` and exactly **one** — `wa_fap`, whose `wa_fap_snap_instead` is scoped to `gc_18plus_no5` and `otherWithWorkPermission` — ships a warning scoped to it. None of the eight Lifeline programs the comment physically sits over ships one; all eight carry only `lifeline_snap_enrollment`, unscoped and about SNAP enrolment. `mo_tanf`, the precedent cited below, declares **no** `warning_messages` at all. So the label stays on the reasoning MFB has already settled, but the banner half of that reasoning is an MFB-wide gap rather than anything this program can close, and no warning is invented here. The DACA and TPS reading does **not** reach this bucket: in benefits-calculator's `citizenshipFilterConfig.tsx`, DACA sits under **`non_citizen`**, whose label is "Undocumented" and whose tooltip reads "Individuals without lawful immigration status (includes DACA recipients)."; `otherWithWorkPermission` is a separate button labelled "Other Lawful". Parole for one year or more falls in that bucket and *is* on §1805.020.10's own qualified-immigrant list. And the same guard test pins `mo_tanf` — a parallel MO state cash program — to exactly `{citizen, gc_5plus, refugee, otherWithWorkPermission}`, this list identically. The four-status list in the config is correct as it stands and needs no change.

6. **Countable income must be strictly below the SAB Consolidated Standard of $1,073/month, effective 2026-01-01**
   - Evaluation scope: `member`
   - Captured via: accessor `HouseholdMember.calc_gross_income(frequency, ["earned", "unearned"], exclude=["sSI"])`, then Missouri's SAB deductions applied to the earned and unearned portions separately — see the implementation note
   - Code divergence: D1 — Missouri's unearned list counts Temporary Assistance and PolicyEngine's does not (see review-notes.md)
   - Code divergence: D2 — Missouri counts investment and interest income, and MFB's `investment` stream reaches no slot SAB's formula reads (see review-notes.md)
   - Implementation note: the test is **exclusive**. Missouri deducts countable income from the Consolidated Standard and requires a remainder, so income *equal to* $1,073 is a denial. **Gross income is not countable income**, and earned and unearned income are treated differently:
     - **Earned income is wider than `EARNED_INCOME_TYPES`.** §0410.015.05 lists "Wages, **Boarders or lodgers**" and self-employment among Missouri's earned sources, and 13 CSR 40-2.050(1)(A) defines earned income as profit from a "business enterprise or farming" — taking in boarders is one. benefits-api's `EARNED_INCOME_TYPES` is `frozenset(("wages", "selfEmployment"))` (`screener/models.py`) and MFB ships a third matching stream, `boarder` (`configuration/white_labels/base.py`). **Implement treats `["wages", "selfEmployment", "boarder"]` as earned.** Leaving `boarder` on the unearned side denies it the exemptions below, raising countable income and excluding claimants Missouri approves. **`rental` is not bundled with it**: 13 CSR 40-2.050(1)(C) makes self-managed real estate earned and agency-managed rental not, and the screener cannot tell them apart — see Data Gap 10.
     - **Earned income** is reduced by the Standard Earned Income Exemption Table — the first $85 plus half the remainder, income and Social Security tax, and a personal standard of 10% of gross earnings (or actual work expenses where greater). Court-ordered alimony and child support, garnished wages and city earnings tax come off after that. The table's own figures are unpublished — see Data Gap 9.
     - **Unearned income** (every other `IncomeStream.type`) carries no standard exemption and counts in full unless separately excluded.
     - **Excluded types** are listed at §0410.015.15 and are not countable at all; the screener cannot distinguish most of them — see Data Gap 10.
     - **No expense side.** The only expenses Missouri considers are standard expense items and the cost of producing income. The first are what the Consolidated Standard consolidates — 13 CSR 40-2.120(3) sets that figure *as* the SAB need budget standard — and the second are the earned-income deductions above. So the test is countable income against $1,073, with no separate expense deduction.
     - **On the recommended engine the arithmetic is PolicyEngine's own, and since 2.17.2 it is Missouri's.** `mo_sab_countable_income` sums `gov.states.mo.dss.ssp.sab.income.sources.{earned,unearned}`, applies the $85-plus-half exemption, subtracts `mo_sab_reported_earnings_taxes` and the 10% personal standard on gross earnings, and deducts court-ordered child support and alimony paid. SSI is absent from its unearned list, so **criterion 8 needs nothing from MFB**. It reads neither `ssi_earned_income` nor `ssi_unearned_income` — zeroing both changed no result when measured on 2026-10-01 — so no `mo_sab`-specific SSI income class is wanted.
     - **A child-support proxy Implement should know is there.** `child_support_received` is added to the claimant's unearned income only when **no** child lives in their SPM unit, and dropped entirely when one does. §0410.015.10 makes support income to the child it is paid for while that child is at home; PolicyEngine labels its own implementation a proxy, because the model does not record whom support is paid for. Where a child is present the direction is **over-inclusive**. `childSupport` is a live screener type, so the branch is modelable, but it gets no scenario: an Expected would have to commit to one side of a proxy PolicyEngine itself calls approximate, and no committed figure here depends on it.
     - **What MFB already supplies** through `dependency.irs_gross_income` — earned: `employment_income`, `self_employment_income`; unearned: `pension_income` (via `taxable_pension_income`), `social_security`, `unemployment_compensation`, `rental_income`, and `retirement_distributions` (via `taxable_ira_distributions`). What it does not reach is D2.
     - **One mapping is required, and it is the boarder rule.** PolicyEngine's earned-source parameter states that "Boarder income and income in kind for services are not captured", and the screener's `boarder` stream reaches no slot the formula reads — so boarder income is invisible and the claimant is paid the full grant whatever they earn from it. Implement declares one dependency class, replacing the shared `EmploymentIncomeDependency` for this program only:

       ```python
       class MoSabEarnedIncomeDependency(IncomeDependency):
           field = "employment_income"
           income_types = ["wages", "boarder"]
       ```

       This is an **input mapping, not an override of PolicyEngine's verdict**. Verified end to end on 2026-10-01 at `frontier` 2.18.0: $1,200/month of boarder income returns countable **$437.50** and eligible, $3,000/month returns **$1,157.50** and ineligible — both exactly Missouri's arithmetic, where without the class both return $0 countable and pay the full grant. `build_pe_input` splits the payload only for a household that actually reports boarder income, so scenario 15 builds two requests where scenarios 7 and 12 build one, and scenario 15 is the case that catches the omission. Shipped MO precedent: `cross_white_label/liheap/mo.py` declares `earned_income_types = ("wages", "selfEmployment", "boarder")` under the comment "Missouri's earned-income definition, which includes roomer-boarder income".

11. **A claimant may hold Temporary Assistance or SAB but not both, and Missouri's guidance is that SAB is usually the better of the two — this is an election, not a bar**
    - Evaluation scope: `member`
    - Captured via: **nothing, and nothing should be** — this is not an eligibility test. A claimant currently drawing Temporary Assistance may elect SAB at any time, so present receipt does not make them ineligible; it tells us only which of the two they hold today.
    - Implementation note: **the two programs are mutually exclusive on the cash, and either side may be the one held.** The SAB manual bars a Temporary Assistance recipient from SAB (§0405.005.00) and the Temporary Assistance manual bars an SAB recipient from TA cash (§0210.005.10) — the same single rule stated from both ends, and both sides describe an election rather than a disqualification: "The individual may elect to receive TA rather than SAB" (§0410.005.05), "Individuals may elect to receive TA rather than SSI, SP, or SAB" (§0210.005.10). **Missouri states which way the election usually runs**: "receiving SSI, SP, or SAB is usually more advantageous than TA". See Benefit Value. **The program description carries the mutual exclusivity, the election and Missouri's recommendation**: that a claimant may hold one or the other but not both, that a Temporary Assistance recipient may choose SAB instead, and that Missouri's guidance is that SAB is usually worth more. The exclusivity sentence was added on 2026-10-02 — the description had carried the election alone, and "you can choose SAB instead" left a reader free to assume they could hold both. The payee-only mechanics stay spec-only; a user who acts on the election learns them from FSD.

## Benefit Value

- Value: **(round($949 − monthly SSI received) × 12) per eligible member** — a maximum of **$11,388/year** where no SSI is received. **The monthly remainder is rounded to the nearest dollar before the ×12**, per 13 CSR 40-2.130(2)(C), with two rules for amounts under a dollar: where the remainder falls between 1¢ and 49¢ Missouri pays $1 rather than rounding to zero — the regulation's own words are "an AB supplemental payment of one dollar ($1)", not quoted above only because the source PDF breaks that phrase across a line — and where it falls between 50¢ and 99¢ ordinary rounding also gives $1. Where the remainder is zero or negative no payment is made. PolicyEngine implements exactly this shape: `np.floor(sab_remainder + 0.5)` with a `(0 < remainder < 1) → 1` special case, over a remainder already floored at zero
- **The rounding step is reachable, because income accepts cents.** `INCOME_AMOUNT_REGEX` in benefits-calculator (`Components/Steps/HouseholdMembers/utils/validation.ts`) is `/^\d{0,7}(?:\d\.\d{0,2})?$/` and `IncomeStream.amount` is a `DecimalField(decimal_places=2)`, so a claimant can report SSI of $500.60 and the unrounded formula would give $5,380.80/year against Missouri's and PolicyEngine's $5,376. This is the **one** place the spec's whole-dollar habit does not hold: `household_assets` genuinely is whole-dollar (`HouseholdAssets.tsx`'s schema is `.int()`, which is why scenario 10 says the cent is unenterable), but income is not. Every scenario below uses whole-dollar SSI, where rounding is the identity, so no Expected moves — the rounding is stated here so a dev implementing the formula by hand does not diverge from the engine on a household that enters cents
- `value_format`: **`null`** (the default, monthly). Set at `config-review` on 2026-10-01, replacing `estimated_annual`. SAB is a recurring monthly cash grant, and benefits-calculator formats on this field: with `null`, `FormattedValue.tsx` divides the stored annual figure by twelve and the results card reads **$949/month**, while the program page keeps the annual total under the label "Estimated Annual Value". With `estimated_annual` the card read "$11,388/year" and the program page labelled it "Average Annual Savings" — *savings* misdescribes a cash entitlement. All four MO recurring-cash siblings (`mo_ssi`, `mo_tanf`, `mo_ssdi`, `mo_medicare_savings`) use `null`. The stored value is unchanged either way, so no scenario Expected moves, and the $1 monthly minimum still clears the results page's `programValue(program) > 0` filter ($12/year → $1/month)
- **The ×12 is the calculator's, not PolicyEngine's.** `mo_ssp` is a `MONTH` variable, so `mo_sab` reads it at **one pinned month** and multiplies by twelve itself. Requesting it at the program year instead returns PolicyEngine's twelve months summed, which blends a mid-year parameter change — and Missouri's SAB figures turn over on July 1. The $1 minimum is monthly too, so it annualises to $12. See Known scenario gaps for the pin.
- Variation axes: the member's monthly SSI amount **as reported**, which is the only axis — once criterion 6 is passed, other income does not reduce the grant. The axis appears in Test Scenarios.
- Implementation note: the offset is the SSI the claimant **receives**, not an SSI entitlement computed for them. A claimant who reports no SSI income receives the full $949, even where a federal model would find them SSI-eligible. This is load-bearing against the recommended engine, because PolicyEngine's `mo_ssp` subtracts its own computed `ssi`. benefits-api already resolves it: `receipt_contract` lowers `takes_up_ssi_if_eligible` for a member reporting no amount, which makes PolicyEngine's `ssi` read 0 for exactly that member. `mo_sab` adopts that contract rather than sending an `ssi` value of its own — see Known scenario gaps.
- **Direction of the no-SSI-reported branch.** Where the claimant reports no SSI, this spec commits the full $949/month. That is what Missouri pays a claimant who receives no SSI, so it is exact for anyone federal SSI cannot reach — a claimant whose resources exceed SSI's own limit, which at $2,000 for an individual and $3,000 for a couple sits far below SAB's $6,220.50 / $12,441.00, or one whose unearned income is at or above roughly $1,014/month, where SSI's computation reaches zero against the $994 federal rate after the $20 general exclusion. It **overstates** for a claimant inside both of SSI's limits who has not yet applied: criterion 5 obliges them to apply where it appears they would be eligible, and once SSI begins the grant falls to roughly (monthly unearned income − $65) × 12. At $300/month of unearned income the committed $11,388 becomes about $2,820. The overstatement direction is disclosed in the config description. **No scenario catches it**, because the screener records only the SSI a claimant reports today — which is the figure Missouri pays on, and the figure this spec is right to use. Scenarios 7 and 9 are exact for the two reasons above; scenarios 6 and 11 sit in the overstating band.
- **The Temporary Assistance interaction moves the household's total, and the direction is not determinable.** The committed figure is **exact for the claimant**: $949 less their reported SSI, which is what Missouri pays them. But a claimant who reports Temporary Assistance is holding the other of two mutually exclusive cash programs (criterion 11), so electing SAB changes the family's Temporary Assistance as well, and **it moves in two directions at once**. §0210.005.10 removes the SAB participant from the Temporary Assistance eligibility unit, which lowers the family's grant for a smaller unit; the same section directs the agency to exclude that person's income and resources from the family's determination, which raises it. Which effect dominates turns on Missouri's Temporary Assistance grant table against the household's own figures, and **no worked example can be committed** — the screener records a single household `cashAssistance` amount, not the assistance unit's composition or the grant's basis. So this spec states the SAB figure and makes no claim about the household's net change. The direction is **not** an overstatement in the SSI sense: that one is a known reduction in the same program, this one is an indeterminate movement in a different one. **No scenario catches it**, and none should — scenario 13 asserts eligibility and the SAB value, which are both exact. The config description carries the trade-off in plain language rather than a figure.
- Source: DSS Manual §0210.005.10 — "Exclude the expenses, income, and resources of the SSI, SP, or SAB participants in determining TA eligibility for the family." — [snapshot `2026-10-01--dss-0210-005-10-ta-excluded-individuals`](../../../sources/mo/mo_sab/2026-10-01--dss-0210-005-10-ta-excluded-individuals/content.md), accessed 2026-10-01

**Known scenario gaps**

- **All 15 scenarios have been run** — 2026-10-01, at `frontier` 2.18.0 and `current` 2.9.0, on a production union payload built by `build_pe_input()` over MO's 18 shipped PolicyEngine calculators. Every Expected is Missouri's answer, derived from source and not conformed to the engine. Evidence: `runs/2026-10-01-mo_sab/pe-rerun-frontier.md`.
- **The couple resource limit cannot be exercised for a married claimant, and no number fixes that.** `SsiCountableResourcesDependency` sends `int(household_assets / num_adults())` per adult, so for a two-adult married household the branches compare `int(A/2)` against the individual limit or `2 × int(A/2)` against the couple limit. The limits are exactly 2:1 from 2026-07-01 ($6,220.50 / $12,441.00), so the branches coincide for every household. Scenario 14 covers the selection from the unmarried side instead.
- **No scenario sits exactly at a resource limit.** The comparison is inclusive and sourced, but `household_assets` is a single undifferentiated total (Data Gap 3), so a scenario at exactly $6,220.50 would assert a precision the input does not carry.
- **Eleven of the twelve data gaps are unscreenable and get no scenario** — 1–8 and 10–12. An Expected would encode a fact the screener cannot observe. **Data Gap 1 is worth naming**, because scenarios 4 and 11 can look like coverage and are not: they exercise the `visually_impaired` boolean, which is the whole of what MFB holds, while the gap is the distance between that boolean and Missouri's 5/200 determination. No scenario can close it.
- **No scenario asserts an exact countable figure derived from earned income.** The exemption structure is sourced but the Standard Earned Income Exemption Table's figures are not (Data Gap 9), and above $1,200/month Missouri directs a manual computation. The two exact-boundary scenarios use unearned income; scenario 12 uses earned income only where every reading of the exemptions gives the same verdict.
- **Every Expected is an annual figure read from one pinned month, and the suite now catches it.** `mo_ssp` is a `MONTH` variable, so an annual request returns PolicyEngine's twelve months summed — and Missouri's figures turn over on July 1. Measured 2026-10-01 at `frontier` 2.18.0 on scenario 7's household, one request asking both periods: `2026-07` returned **$949.00** (× 12 = **$11,388.00**) and `2026` returned **$11,196.00**, a difference of exactly **$192.00** (evidence: `annual-read-probe.json`). So a calculator reading `mo_ssp` annually fails scenarios 1, 2, 6, 7, 9, 13 and 15 by $192 and scenario 11, a two-member household, by $384. **Scenario 3 is the one eligible row it does not catch** — its remainder floors at zero in both halves. Before 2.17.2 nothing caught the pin, because the 2026 parameter was flat at $917. The build instruction is in the companion's Build requirements.
- **No scenario covers a blind student aged 18–21 with earnings.** The branch is modelable — `student`, `student_full_time` and `birth_year_month` all exist — but an Expected would run through Data Gap 9's unpublished table, and above $1,200/month gross no table applies at all (§0410.015.05.20 sends the caseworker to compute manually). **The branch carries no engine divergence**: Missouri grants no student exclusion and neither does PolicyEngine — read at `policyengine-us` `origin/main` `6c5170fd` (2.20.1), `mo_sab_countable_income` deducts the §0410.015.05.20 stack and nothing else, and its own comment says there is no SSI student exclusion. `is_full_time_college_student` still arrives from MO's SNAP, TANF and CDCC calculators, but nothing in the SAB chain reads it.

### Scenario 14: Blind adult living with a parent — the individual limit applies — Ineligible
**What we're checking**: criterion 9 — an unmarried claimant takes the individual resource limit, whatever the shape of the household around them.
**Expected**: Ineligible (the claimant's $8,000 share exceeds the $6,220.50 individual limit). Person 1 is not blind and is ineligible on criterion 2.
**Steps**:
* Location: ZIP `65101`, county `Cole County`
* Person 1: born March 1966 (age 60), head of household, blind/visually impaired `No`, income: Wages `$3,000`/month
* Person 2: born March 2004 (age 22), child, blind/visually impaired `Yes`, income: Pension `$400`/month, no SSI reported
* Household assets `$16,000`
**Why this matters**: the mirror of scenario 9, and the only scenario in which the couple limit must **not** be selected. Every other gate passes for Person 2, so resources are the only thing that can deny and the case is so nothing else can cause the denial. The $16,000 gives her a per-adult share of $8,000 — above the $6,220.50 individual limit and below the $12,441.00 couple limit, so the two limits give opposite verdicts and nothing else does. She is unmarried, so Missouri applies the individual limit and denies.

**Against the recommended engine this scenario now returns ineligible — matching the Expected. Confirmed by run.** Re-run on 2026-10-01 at `frontier` **2.18.0**: `mo_ssp_resource_eligible` **False**, `mo_ssp` **$0**. Her $8,000 share — `int(16000/2)`, from `SsiCountableResourcesDependency` — is compared against the **individual** limit $6,220.50, because PolicyEngine 2.17.2 selects on `person.marital_unit.nb_persons() == 2` and this household sends `"marital_units": {}` (`Screen.relationship_map()` pairs only spouses and domestic partners), so policyengine-core gives her a marital unit of one. **It also returns ineligible on the un-fixed 2.9.0**, because the production payload sends `is_tax_unit_spouse = False` for her from `dependency.member.TaxUnitSpouseDependency`, which `MoSsi` puts on every Missouri request. With that flag sent, `spm_unit_is_married` is False and the individual limit applies **before** any upstream fix. A payload declaring only `mo_sab`'s own inputs would instead let PolicyEngine rank the oldest non-head adult, return True, and apply the couple limit — the reason a one-calculator harness cannot measure this scenario. That result was reproduced exactly on 2026-10-01 by withholding the single field. **So B4 was a real PolicyEngine defect, correctly filed and correctly fixed, but it was never reachable on the payload a Missouri screen sends.** The fix's effect here is that the verdict no longer depends on the flag: withheld, 2.18.0 still denies. **What this scenario still catches.** It remains the only coverage of the limit selection: a build that applies the couple limit unconditionally returns eligible at $949/month, and one that omits `SsiCountableResourcesDependency` sends no resources at all and returns eligible. Both die here. It no longer catches `is_tax_unit_spouse`, because on 2.18.0 neither value changes the verdict. Evidence: `runs/2026-10-01-mo_sab/pe-rerun-frontier.md`, counterfactual C1.

### Scenario 15: Boarder income under Missouri's earned-income exemptions — Eligible, $11,388
**What we're checking**: criterion 6 — Missouri counts income from boarders and lodgers as **earned**, so it carries the earned-income exemptions. A build that leaves `boarder` on the unearned side gives it no exemption and denies.
**Expected**: Eligible — $11,388/year
**Steps**:
* Location: ZIP `65101`, county `Cole County`
* Person 1: born March 1986 (age 40), head of household, blind/visually impaired `Yes`, income: Boarder or Lodger Income `$1,200`/month, no SSI reported
* Household assets `$1,000`
**Why this matters**: Missouri counts boarder and lodger income as **earned**, so it carries the earned-income exemptions. The exemption is at least $85 + ½ × $1,115 = $642.50, so countable is at most $557.50 — well under $1,073. **The Expected therefore does not depend on Data Gap 9**: every reading of the table can only make the exemption larger, so the verdict is the same either way, and the same on both sides of the $1,200 boundary at which §0410.015.05.20 sends the caseworker to compute manually. The value is the no-SSI-reported branch. **Whether this scenario catches the mapping depends on `MoSabEarnedIncomeDependency` being declared** — see the run below.

**Against the recommended engine this scenario depends on criterion 6's boarder mapping — confirmed by run both ways.** Re-run 2026-10-01 at `frontier` **2.18.0** with the shared `EmploymentIncomeDependency`, PolicyEngine never sees the boarder income: `mo_sab_countable_income` returns **$0** and it pays the full $949/month. The verdict matches the Expected by accident, and the scenario catches nothing — neither of the two bugs it aims at can be reproduced, because no MFB field reaches the variable. PolicyEngine's earned-source parameter says as much: "Boarder income and income in kind for services are not captured". **With `MoSabEarnedIncomeDependency` declared it is exact**: countable **$437.50** — `($1,200 − $85) × 0.5 − $120` — eligible, `mo_ssp` **$949/month** = **$11,388/year**. The $120 is the 10% personal standard, new in 2.17.2 and absent from the SSI-style arithmetic the pre-fix trace assumed, which is why the old figure was $557.50; both are far under the $1,073 standard, so the verdict holds on either. **The mapping is what the scenario tests, and it bites**: at $3,000/month of boarder income the same build returns countable **$1,157.50** and **ineligible**, matching Missouri, where without the class PolicyEngine pays $949/month to a claimant Missouri denies. Evidence: `runs/2026-10-01-mo_sab/pe-rerun-frontier.md`, counterfactual C3.
